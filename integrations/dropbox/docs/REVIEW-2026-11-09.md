# Dropbox review against the Excel baseline

Release: 2.0.4. Build: dropbox-composio-v6-card-review. Exactly 14 approved tools; eight write confirmations. Account setup and the pinned Dropbox toolkit version remain unchanged.

## Reference

Reviewed Excel HANDOFF.md and docs/review-follow-up-2026-11-08.md, plus its current generated confirmation CSS and headless Chrome tests. This is a local-file comparison, not direct access to another conversation. Dropbox now applies the same separated footer, conditional form scrolling, editable target fields and real-browser regression approach.

## Changes

- All write confirmations use a 64px opaque host-button footer, independent form scrolling, aligned icons/titles and readable labels. Upload behavior uses an Add/Overwrite select. Every write argument is editable through the existing bridge; there are no dummy preview targets.
- Results retain normal returned collections in a scrollable area instead of showing only six entries. Paths, sizes, revisions and timestamps are shown when returned. Large HTML payloads have a disclosed display budget; complete provider data remains available to the agent. Binary retrieval does not claim to have parsed a spreadsheet or document.
- Shared links are clickable only for Dropbox HTTPS destinations. Signed download URLs are not exposed as card links. Green success checks follow completed calls; failures and unknown outcomes cannot display success.
- Background failure text is plain language, with machine/card data in structuredContent, so hosts that print error text do not dump JSON/HTML. A rendering failure after a completed operation preserves its success and data rather than inviting a duplicate write.
- Requests now stop at 45 seconds, below the observed host timeout. MCP cancellation propagates to account/catalog/action requests; cancellation after dispatch reports unknown write outcome. SDK execution remains single-attempt with no automatic write retries.
- Conflicting wrappers, cyclic/excessive wrappers, malformed collection rows, control/dot path segments and case-insensitive copy/move destination collisions fail closed. Error handling redacts credentials and signed query strings while keeping setting names readable. Composio API-key problems are distinguished from Dropbox OAuth-token problems.
- Setup utility errors consistently return JSON and share the redaction logic.

## Verification and limits

The offline suite includes 64 browser confirmation cases: all eight writes, widths 320/480, host button lifts 40/56, dark/light. It verifies field visibility, footer coverage, no outer overflow, argument hydration and edited-value bridge events. Result scrolling is checked to the last of 30 returned items. Other regressions cover MCP discovery, manifest parity, single-write counts, account validation, malformed envelopes, cancellation, redaction and truthful success/failure rendering.

No live Dropbox write was performed. The attempted read-only catalog audit could not authenticate outside VoiceOS because saved credentials are encrypted by the host. This is not evidence of an invalid user API key. Pinned-schema validation still runs before actions; provider mappings have not been changed speculatively. Manual QA inside VoiceOS is required for live schema conformance and every write action. Phase progress is available, but byte progress and global toast rendering still require host/provider support.

Final local checks: npm run build and npm test completed with 57 tests, zero failures and no skipped browser cases. The installed release was verified under VoiceOS's bundled Bun with matching manifest/package/MCP version 2.0.4 and 14 tools. The stale Bun lockfile was refreshed; the installed pinned dependency set passed a frozen-lockfile install. The cached installed manifest was updated with credentials and unrelated settings preserved. Live confirmation cancellation and Dropbox writes remain manual QA.
