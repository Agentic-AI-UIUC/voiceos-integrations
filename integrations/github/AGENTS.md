# Working on this VoiceOS integration (guide for AI coding agents)

You are editing **GitHub**, a VoiceOS integration generated by the
VoiceOS Integration Studio: a folder that teaches the VoiceOS voice agent new
tools, with native UI in the Mac notch. This file is the whole contract — no
VoiceOS internals needed.

## What a user experiences

The user talks to VoiceOS. The agent picks one of the tools declared here,
VoiceOS runs this folder's MCP server (`server.ts`), and the result appears
two ways: the model narrates the data, and the notch shows the tool's
**glance card** (the `_voiceos_glance` blocks the tool attaches to its
result). Tools that act on the user's behalf first show a **confirmation
card** declared in the manifest, which the user can edit and approve.

## Files

- `voiceos.integration.json` — identity, runtime, permissions, tools
  (name/description/inputSchema/confirmation). Every manifest tool must be
  registered in server.ts with the same name, and vice versa. Keep
  `runtime` exactly as generated — VoiceOS resolves it to the launcher for
  the user's OS.
- `server.ts` — standard MCP stdio server (@modelcontextprotocol/sdk + zod).
- `run.sh` / `run.cmd` — the launchers VoiceOS invokes (macOS / Windows);
  leave them alone.
- `package.json` — add dependencies here, then `bun install`.
- `icon.png` / `studio-meta.json` — the Studio's icon and preview fixtures;
  safe to leave untouched.

## Rules that make integrations feel native

1. **Tool descriptions are routing rules for the model**: what it does + when
   to use it ("Use when the user asks …").
2. **Results carry data AND a glance card**: JSON the model reasons about,
   plus a `_voiceos_glance: { blocks: [...] }` key spread into the result
   for the user. Never put information only in the card.
3. **Glance cards are a 2-second read** — max 3 blocks. Vocabulary:
   `header` {icon?, title, trailing?}, `list` {header?, rows: [{icon?,
   title, subtitle?, trailing?, badge?: {text, tone?}}]} (≤6 rows), `stats`
   {items: [{label, value, delta?, tone?}]} (≤3), `keyValue` {pairs:
   [[label, value]]} (≤5), `bars` {labels, values, unit?} / `line`
   {points, tone?, baseline?} / `splitBar` {segments} (max ONE chart),
   `progress` {value, max?, label?, style?: "bar"|"ring"}, `badges`
   {items} (≤3), `clock` {tz}, `countdown` {until|seconds}, `divider`,
   `row` {children} (2-3 side by side). tone is "neutral"|"good"|"bad".
   Titles ≤60 chars; pre-trim strings. Off-schema blocks are silently
   dropped.
4. **Anything that acts needs a manifest `confirmation` card.** Inputs bind
   to args with `{{argName}}`; edited values are what execute. Interactive
   vocabulary: card, stack, text, markdown, keyValue, metadata, list/listItem,
   image, badge, divider, progress, textField, passwordField, select, toggle,
   chips (inputs take `bind`), actions (roles confirm/cancel/copy/openUrl —
   exactly one confirm and one cancel, in a footer actions block). Read-only
   tools must NOT declare one.
5. **Be honest**: throw on failure; never fabricate data or claim success.
   Use `console.error` for debug logging (stdout is the MCP wire).
6. **Least privilege**: the manifest's network permission lists only domains
   the code actually calls.
7. **Long work (>20s) declares** `"execution": {"mode": "background"}` +
   the `background` permission.
8. **Secrets come from the user**: declare manifest `preferences` (type
   "password" for secrets); VoiceOS injects them as env vars named after each
   field (`process.env.MY_FIELD`). Never hardcode keys.

## Dev loop

```bash
bun install        # once, and after adding dependencies
bun server.ts      # starts the MCP server; Ctrl-C when it idles cleanly
```

Then in VoiceOS: Dashboard → Agent tab → Integration Studio → My
Integrations → open **GitHub** → **Reload**. The agent sees your
changes on its next turn — just talk to it.

## Definition of done

- Manifest tools and server.ts registrations match exactly.
- Each tool description says when the model should call it.
- Acting tools have confirmation cards; read tools don't.
- Glance cards read in 2 seconds.

## This integration (read before editing)

- **Edit `src/`, then rebuild.** `server.ts` is a generated bundle, and the
  manifest's `tools`, `preferences` and `description` come from
  `scripts/build.ts`. Run `bun run build`; never hand-edit `server.ts` or the
  manifest's tools.
- **Check every change:** `bun run build && bun test && bun run verify`.
- **The tool list is fixed at eight** (`src/catalog.ts`, the approved
  allowlist). The integration works with every repository the connected
  GitHub account can reach; there's no repository limit.
- **SOC 2 review is warn-only for QA (v2.5.4).** Keep the warning on the
  integration page and every result/confirmation card (`src/reviewWarning.ts`).
  All eight tools and connection warm-up remain available. Production
  approval is tracked on the VoiceOS side: In Review → QA → switch to the
  VoiceOS Composio key → publish. There is no repository sign-off JSON or
  code fingerprint gate. Maks decides the final policy and reviewers.
- **Writes depend on their confirmation cards.** Each write card stages a
  receipt: a keyless SHA-256 digest of the exact arguments on screen
  (`src/receiptCoreScript.ts`), which the server recomputes. A card whose
  receipt code doesn't match the server's fails closed. No key or secret may
  go in the manifest: the share review rejects it. Card markup lives in
  `src/confirmations.ts`, result cards in `src/cards.ts`.
- **Results are plain facts; Agent Mode writes the answer** (Dario's rule,
  2026-10-28). Each result carries trimmed data (number, title, state,
  author, a short description excerpt), every item's `html_url`, the total
  and top five for searches, plain-word error messages, and for changes what
  was created or changed with its link. Never add narration for the agent to
  repeat: `src/speech.ts` and its `spoken` lines were removed. Tool descriptions in `src/catalog.ts`
  only describe the tool and its results: VoiceOS's share review rejects
  descriptions that tell the agent how to answer or which tools to avoid
  (`tests/manifest.test.ts`).
- **Built to pass VoiceOS's share review** (published as a share link, which
  teammates install). The runtime is `bun server.ts`, not the generated
  `/bin/zsh run.sh`: the review rejects a shell. `run.sh`/`run.cmd` stay but
  aren't used. Nothing may compile code from a string (`new Function`,
  `eval`): the receipt core lives in `src/receiptCoreScript.ts`, which the
  server imports and whose exact text the cards get at build time.
- **`server.ts` carries its dependencies.** A shared install is only five
  files with no `node_modules`, and Bun's automatic install picks the latest
  zod instead of the pinned one. `scripts/build.ts` inlines everything,
  switches off zod 4's code generation and replaces the SDK's ajv validator
  (Composio's tools declare no output schemas). `bun verify.ts --package`
  runs the shared files alone with an empty Bun cache.
- **Cards carry facts and the required SOC 2 review footer:** no other
  explanatory notes or "click to send" lines (`tests/cards.test.ts`,
  `tests/confirmations.test.ts`).
- **A spoken yes can't approve a change.** VoiceOS drops the card's staged
  receipt on voice approval, so the server refuses and hands the draft back
  once (`ReceiptMissing` in `src/gateway.ts`). Don't weaken the receipt check
  to make voice approval work.
- **No secrets anywhere.** The Composio key arrives as
  `COMPOSIO_PROJECT_API_KEY`. Connect links reach only the card, never the
  model's data. `.state/` holds no keys or tokens.
- **When Composio changes a schema**, the audit log records
  `upstream_schema_changed`. Review it, then update
  `tests/fixtures/composio-mcp-tools-list.json` (captured from a live session)
  and `UPSTREAM_SNAPSHOT` in `src/catalog.ts` together.
