# Working on this VoiceOS integration (guide for AI coding agents)

You are editing **TikTok**, a VoiceOS integration first generated by the
VoiceOS Integration Studio: a folder that teaches the VoiceOS voice agent new
tools, with native UI in the Mac notch. This file is the whole contract — no
VoiceOS internals needed.

Unlike a fresh Studio folder, the code here lives in `src/` and
`confirm-card/`, and `bun run build` turns it into `server.ts` and
`voiceos.integration.json`. Read "This integration" at the end before you
edit anything. `handoff.md` has the status, the decisions and what's left;
`README.md` is the user-facing page.

## What a user experiences

The user talks to VoiceOS. The agent picks one of the tools declared here,
VoiceOS runs this folder's MCP server (`server.ts`), and the result appears
two ways: the model narrates the data, and the notch shows the tool's
**glance card** (the `_voiceos_glance` blocks the tool attaches to its
result). Tools that act on the user's behalf first show a **confirmation
card** declared in the manifest, which the user can edit and approve.

## Files

VoiceOS Publish ships only five files: `server.ts`, `widgetKit.ts`,
`voiceos.integration.json`, `package.json` and `icon.png`. A shared install
has no `node_modules`, so `server.ts` has to carry everything it needs.

Shipped:

- `voiceos.integration.json` — identity, runtime, permissions, tools
  (name/description/inputSchema/confirmation). Every manifest tool must be
  registered in server.ts with the same name, and vice versa. **Generated** by
  `bun run build`: names, descriptions and input schemas come from the
  running server's `tools/list`, titles/visibility/execution from `TOOL_META`
  in `src/tools.ts`, and the four confirmation widgets from `confirm-card/`.
  Don't hand-edit it.
  - `runtime` is `{ "kind": "local-mcp", "command": "bun", "args": ["server.ts"] }`,
    written by the build. It deliberately differs from Studio's generated
    `/bin/zsh run.sh`: VoiceOS's share review rejects a shell runtime, and a
    shared install has no `run.sh`. Keep `runtime` exactly as the build
    writes it.
  - `id` is `com.voiceos.generated.tiktok`. Never change it: VoiceOS keys
    settings and secrets off it.
- `server.ts` — standard MCP stdio server (@modelcontextprotocol/sdk + zod).
  **Generated**: a self-contained bundle of `src/` with the SDK and zod
  inlined. Don't hand-edit it; the next build overwrites it.
- `widgetKit.ts` — the VoiceOS Widget Kit that every card is built with.
  Don't edit it. It embeds the integration's logo as `INTEGRATION_MARK` and
  draws it in card headers.
- `package.json` — pinned dependencies (MCP SDK 1.32.2, zod 3.25.76, tsx)
  and the `build`, `test` and `verify` scripts. Add dependencies here, then
  `bun install`, and pin exact versions: the build bundles them into
  `server.ts`, because a shared install can't install them.
- `icon.png` — currently TikTok's logo. TikTok forbids using its logos
  without permission; see "Before you ship" in `handoff.md`.

Source and tooling (not shipped):

- `src/` — the runtime code:
  - `main.ts` (entry point) and `mcpServer.ts` (creates the server and
    registers the 12 tools);
  - `tools.ts` (tool metadata `TOOL_META` and handlers), `results.ts`
    (result shaping), `ledger.ts` (recent writes and the one-at-a-time
    write queue);
  - `client.ts` (Composio REST v3.1: pinned toolkit version, account check,
    video staging, argument builders) and `ratelimit.ts`;
  - `receipts.ts` and `receiptCoreScript.ts` (confirmation receipts; the
    cards run the same receipt core), `tokens.ts` (file, image, bundle and
    post tokens), `state.ts` (atomic state files);
  - `files.ts` and `media.ts` (finding videos and photos, the MP4/MOV
    reader, `sips` metadata, Content Credentials), `images.ts` (the photo
    conversion pipeline), `relay.ts` (media relay client);
  - `cards.ts`, `format.ts`, `captions.ts` (result cards, numbers and
    dates, caption limits and parsing), `errors.ts` (our error codes,
    TikTok's code maps, and every user-facing error line);
  - `config.ts` (constants, setup fields, test arguments), `proc.ts`
    (child processes with kill timers, `log()`), `types.ts`.
- `confirm-card/` — the four write confirmation widgets. The only place
  confirmation HTML is written.
- `scripts/build.ts` — `bun run build`. `scripts/pull-schemas.ts` pulls
  Composio's tool schemas at the pinned version (spike S3; needs a real key,
  reads only). `scripts/render-cards.ts` renders the result cards for a
  visual check.
- `tests/` — `bun test`: unit tests, a loopback mock Composio
  (`mock-composio.ts`), a mock relay (`mock-relay.ts`) and tiny fixtures.
- `verify.ts` — `bun run verify` launches `server.ts` on VoiceOS's bundled
  Bun and calls the tools; `bun verify.ts --package` runs the five shared
  files alone with an empty Bun cache (a teammate's first launch).
- `voiceos.integration.preview.json` and the `preview` block of
  `studio-meta.json` — preview fixtures, written by the build, read tools
  only. `studio-meta.json` also keeps the original Studio brief.
- `run.sh` / `run.cmd` — the launchers Studio generated. Unused here (see
  `runtime` above); leave them alone.
- `handoff.md`, `README.md`, `.env.example`, `.gitattributes`, and the
  spec: `context.md` (ticket context, the authority),
  `UIUC-2-tiktok-implementation-plan.md` (the plan, v3),
  `UIUC-2-verification-log.md` (evidence and tested snippets).

## Rules that make integrations feel native

1. **Tool descriptions are routing rules for the model**: what it does + when
   to use it ("Use when the user asks …").
   - Here: the 12 descriptions are the approved wording, defined with the
     tools in `src/tools.ts`. Each one says "Use when"; agent-only ones start
     with "Agent-only", and writes say "Runs in the background". Avoid the
     words VoiceOS's share review rejected on 2026-10-28 (never, don't,
     stop, verbatim, "spoken yes"), here and in the manifest description
     and the server's MCP instructions (`CAPABILITY_GUIDANCE` in
     `src/mcpServer.ts`). `tests/manifest.test.ts` checks all of it. Never
     put TikTok content (captions, names) in a description.
2. **Results carry data AND a glance card**: JSON the model reasons about,
   plus a `_voiceos_glance: { blocks: [...] }` key spread into the result
   for the user. Never put information only in the card.
   - Here: `content: [{ type: "text", text: JSON.stringify({ ...data, _voiceos_glance }) }]`.
     Failures return `isError: true`, plain words and an error card. Results
     that carry captions, titles or names add the untrusted-content note
     (`UNTRUSTED_NOTE` in `src/captions.ts`).
3. **Glance cards are a 2-second read** — max 3 blocks. Vocabulary:
   `header` {icon?, title, trailing?}, `list` {header?, rows: [{icon?,
   title, subtitle?, trailing?, badge?: {text, tone?}}]} (≤6 rows), `stats`
   {items: [{label, value, delta?, tone?}]} (≤3), `keyValue` {pairs:
   [[label, value]]} (≤5), `bars` {labels, values, unit?} / `line`
   {points, tone?, baseline?} / `splitBar` {segments} (max ONE chart),
   `progress` {value, max?, label?, style?: "bar"|"ring"}, `badges`
   {items} (≤3), `clock` {tz}, `countdown` {until|seconds}, `divider`,
   `row` {children} (2-3 side by side). tone is "neutral"|"good"|"bad".
   Titles ≤60 chars; pre-trim strings. Off-schema blocks are silently
   dropped.
   - Here: result cards are widgetKit widgets (`src/cards.ts`), 60–420 px
     tall, one accent colour (`ACCENT`, `#fe2c55`). Escape every string with
     `esc()`. Images only as `data:` URIs: widgets have no network.
4. **Anything that acts needs a manifest `confirmation` card.** Inputs bind
   to args with `{{argName}}`; edited values are what execute. Interactive
   vocabulary: card, stack, text, markdown, keyValue, metadata, list/listItem,
   image, badge, divider, progress, textField, passwordField, select, toggle,
   chips (inputs take `bind`), actions (roles confirm/cancel/copy/openUrl —
   exactly one confirm and one cancel, in a footer actions block). Read-only
   tools must NOT declare one.
   - Here: the four writes (`upload_video`, `publish_video`,
     `upload_photos`, `post_photos`) use **widget** confirmations from
     `confirm-card/` instead of the native vocabulary. Keyed inputs carry
     `data-voiceos-key="<argName>"` and stage edits with
     `voiceos:updateInput`. A widget has no actions block: VoiceOS floats its
     own confirm button (labelled by `confirmLabel`), and there's no Cancel
     button (the user says no or dismisses the card). Every key a card
     stages must be in that tool's `inputSchema` (`CARD_KEYS`). Reads and
     the agent-only helpers have no confirmation.
5. **Be honest**: throw on failure; never fabricate data or claim success.
   Use `console.error` for debug logging (stdout is the MCP wire).
   - Here: log with `log()` from `src/proc.ts` (stderr). A write's outcome
     is only what Composio or TikTok returned. A lost answer to a write is
     `OUTCOME_UNKNOWN`, never success and never retried. See "Logging"
     below for what may never be logged.
6. **Least privilege**: the manifest's network permission lists only domains
   the code actually calls.
   - Here: `backend.composio.dev` and Composio's real presigned-upload
     host, a Cloudflare R2 bucket (`COMPOSIO_UPLOAD_HOST` in
     `src/config.ts`, confirmed live in spike S2; the first upload logs
     the host if it ever changes). The build adds the relay
     host once `MEDIA_RELAY_BASE` is set. It also adds TikTok's two image
     CDN hosts (`TIKTOK_IMAGE_HOSTS` in `src/config.ts`): `src/covers.ts`
     fetches profile pictures and post covers from them and puts them in
     result cards as small `data:` images.
7. **Long work (>20s) declares** `"execution": {"mode": "background"}` +
   the `background` permission.
   - Here: the four writes are background tools (120 s estimate for
     drafts, 180 s for direct posts). Reads and helpers are sync: a
     Composio request gets 8 s, and a whole read 20 s at most.
8. **Secrets come from the user**: declare manifest `preferences` (type
   "password" for secrets); VoiceOS injects them as env vars named after each
   field (`process.env.MY_FIELD`). Never hardcode keys.
   - Here: `COMPOSIO_API_KEY` (password), `COMPOSIO_USER_ID` (text, default
     "default"), `COMPOSIO_CONNECTED_ACCOUNT_ID` (text) and
     `MEDIA_RELAY_TOKEN` (password, optional), all temporary. Only
     `loadConfig` in `src/config.ts` reads them. An undeclared preference is
     silently empty. No key may go in the manifest: the share review
     rejects it.

## Dev loop

```bash
bun install              # once, and after adding dependencies
# edit src/ or confirm-card/
bun run build            # src/ → server.ts; writes voiceos.integration.json and the preview fixtures
bun test                 # unit tests against loopback mocks
bun run verify           # server.ts on VoiceOS's bundled Bun, as VoiceOS runs it
bun verify.ts --package  # the five shared files alone, empty folder and Bun cache
bun server.ts            # optional: starts the MCP server; Ctrl-C when it idles cleanly
```

Then in VoiceOS: Dashboard → Agent tab → Integration Studio → My
Integrations → open **TikTok** → **Reload**. The agent sees your
changes on its next turn — just talk to it. VoiceOS caches the manifest in
`~/Library/Application Support/VoiceOS/config.json`; if a change doesn't
show after Reload, quit and reopen VoiceOS.

**Don't use Integration Studio's "Edit with AI → Save" on this folder.** It
reinstalls the folder with only `server.ts` and the manifest, which deletes
`src/`, `tests/`, `confirm-card/` and `scripts/`. Edits made to `server.ts`
directly are lost at the next build anyway.

## Definition of done

- Manifest tools and server.ts registrations match exactly.
- Each tool description says when the model should call it.
- Acting tools have confirmation cards; read tools don't.
- Glance cards read in 2 seconds.
- For this folder, also:
  - `bun run build && bun test && bun run verify` pass, and
    `bun verify.ts --package` passes before any Publish;
  - the tools are still the approved 12, and the four photo tools stay
    `disabled` while `MEDIA_RELAY_BASE` is empty;
  - no write ran against real Composio or TikTok;
  - `handoff.md` says what changed and what you couldn't test.

## This integration (read before editing)

- **Edit `src/` and `confirm-card/`, then rebuild.** `server.ts`, the
  manifest and the preview fixtures are build output.
- **The tool list is fixed at 12**, as approved for UIUC-2: four reads
  (`get_user_stats`, `list_videos`, `query_videos`,
  `fetch_publish_status`), four agent-only helpers (`query_creator_info`,
  `find_recent_videos`, `find_recent_images`, `prepare_photo_post`) and
  four writes. `TIKTOK_PUBLISH_VIDEO` (URL pull) and `TIKTOK_UPLOAD_VIDEOS`
  (batch) stay unexposed. Adding a tool needs syafino's sign-off first.
- **Slugs.** `upload_video` → `TIKTOK_UPLOAD_VIDEO` with `publish: false`;
  `publish_video` → `TIKTOK_UPLOAD_VIDEO` with `publish: true`;
  `upload_photos` / `post_photos` → `TIKTOK_POST_PHOTO` with `post_mode`
  `MEDIA_UPLOAD` / `DIRECT_POST`. Every execute call pins
  `TIKTOK_TOOLKIT_VERSION` (`20261101_00`, `src/config.ts`). Bump it only
  after `scripts/pull-schemas.ts` and the live matrix.
- **Consent is checked by the server.** Each confirmation card stages a
  `confirmation_receipt`: a SHA-256 digest of the exact arguments on screen,
  with a time and a nonce (`src/receiptCoreScript.ts`; the cards inline the
  same text). The server sends a write only with a receipt that matches the
  arguments, is at most 10 minutes old and hasn't been used. Spent digests
  persist in
  `~/Library/Application Support/VoiceOS/integration-state/com.voiceos.generated.tiktok/spent-receipts.json`
  (digests only), so a restart doesn't reopen them. All checks run before
  anything is uploaded. Don't weaken this to make voice approval work:
  VoiceOS 0.1.40 drops the card's staged values when the user says "yes",
  so a spoken yes is refused (`CONFIRMATION_REQUIRED`). The writes carry
  `hidePermissionToggle: true`; "Ask before every action" must stay on.
- **Card values are untrusted.** Labels, `warning`, the `*_disabled` flags,
  `privacy_options` and `creator_nickname` come from the agent. The server
  re-checks them against its own tokens, and re-applies TikTok's
  direct-post rules (privacy picked and allowed, disclosure complete, no
  branded content as Only me, duration within the creator's limit,
  creator-disabled interactions forced off).
- **Tokens, not paths.** The model never sees a file path. The helpers
  mint HMAC tokens with a random per-process key (`src/tokens.ts`):
  `file_token` 15 min, `image_token` 30 min, `bundle_token` 30 min,
  `post_token` 10 min. A server restart invalidates all of them
  (`TOKEN_STALE`). Results show basenames and folder names only.
- **Writes** run in the background, one at a time per account. A write is
  never retried. Status polling waits 5, 10, 20 and 40 s, then every 60 s,
  for up to 30 minutes. Return the final card only at the end: returning
  early ends the VoiceOS task. That completion card is the ticket's "toast".
- **Photo tools ship disabled** while `MEDIA_RELAY_BASE` in
  `src/config.ts` is empty. They are implemented and have tests against a
  mock relay. To switch them on, set `MEDIA_RELAY_BASE` and rebuild: the
  build adds the relay host to the network permission and drops
  `disabled`. Testers then set `MEDIA_RELAY_TOKEN`.
- **No code compiled from strings** in anything that ships: no `eval`, no
  `new Function`, no `setTimeout("…")`, no code-generating validator. The
  build patches zod and stubs the SDK's ajv validator for this. The `sips`
  canvas script in `src/images.ts` is data: it's written to a temp file and
  run by `sips -j`, never evaluated by us.
- **Logging.** stderr only, through `log()`. Log the slug, the duration, our
  error code, TikTok's `log_id` and the relay batch-id prefix (6 chars).
  Never log the API key, the connected account id, the relay token, file
  paths (a basename at most), captions, titles, descriptions, nicknames, or
  presigned and relay URLs.
- **Tests.** `bun:test`, files in `tests/` named `*.test.ts`. The club CI
  runs `bun install` and `bun test` on ubuntu-latest, so unit tests inject
  a fake `Runner` instead of calling `sips`, `mdls`, `osascript`,
  `defaults`, `qlmanage` or `pbcopy`. Real-tool suites go behind
  `test.skipIf(process.platform !== "darwin")`. Composio and the relay are
  loopback mocks (`--composio-base-url` and `--media-relay-base` accept
  only 127.0.0.1 or localhost). **Never call real Composio or TikTok from
  a test, and never give a write a preview fixture**: VoiceOS's previewer
  and `verify.ts` really run what they're given.
- **Bun loads a `.env` from this folder automatically**, for `bun test`,
  `bun server.ts` and VoiceOS's own launch, and it fills any setting VoiceOS
  leaves empty. Don't keep one with real values here; never commit one.
- **Setup fields are temporary** (Excel pattern) and must be removed before
  release; `handoff.md` tracks the replacement.
